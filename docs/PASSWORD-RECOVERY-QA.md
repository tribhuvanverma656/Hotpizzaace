## Earlier email recovery approach and configuration

Release `c6c17a1` introduced the proposed email-recovery journey **open email → enter the new website password twice → Save**. Its passive `/auth/confirm` page accepted a private token only from its URL fragment, captured it in component memory and removed the fragment. A GET did not verify or consume it. Passwords and tokens were not persisted to browser storage. A refresh required reopening the email. Google and password sign-in remained available.

In that release, one same-origin POST to `/api/auth/recovery` validated bounded input and matching passwords before `verifyOtp({ token_hash, type: 'recovery' })`. It independently verified the exact newly returned token and matching confirmed identity, required recent OTP/recovery claims, updated the password in that same request and then attempted global sign-out. Ordinary existing OTP or Google sessions could not use the separate recovery-only password-update route. Provider errors and client notices excluded private token/password values. A failed response after consuming a token required a new email; a committed password update was not described as failed solely because sign-out failed. Those email-recovery/update endpoints now fail closed.

The complete local suite passed **240 tests**, lint, formatting, TypeScript and an isolated production build. **44 authentication smoke checks passed locally and live**. New tests exercise the installed SDK and SSR cookie adapter from empty cookies, the real request sequence through verification/update/sign-out, token replay, existing-session rejection, password validation before consumption, malformed/duplicate/oversized input, origin checks and fragment parsing. A local browser confirmed the blank password form appears and the fragment is removed. These results do not establish a live owner password change.

At that stage, the connected Supabase dashboard required **custom SMTP or Pro to customize email templates**. Custom SMTP was disabled and the fixed reset template still pointed through the provider verification URL. No SMTP, paid plan or hosted template was changed. A replacement template was prepared at `supabase/templates/recovery.html` but was not activated. The release gated password-email requests behind `NEXT_PUBLIC_PASSWORD_RECOVERY_ENABLED=false` pending sender/template validation. The owner subsequently deferred email recovery; the current sign-in UI removes those controls and the email-recovery/update endpoints fail closed regardless of that earlier feature flag.

SMTP/template configuration was a dependency of that proposed email approach. It is not a dependency of the accepted Google-authorized owner password workflow. Configuring a sender or re-enabling email recovery is deferred future scope, not a current password-acceptance task. No password or reset link should be shared in chat.

Primary references: [Supabase email templates and email prefetching](https://supabase.com/docs/guides/auth/auth-email-templates), [TokenHash verification](https://supabase.com/docs/reference/javascript/auth-verifyotp), and [adding password sign-in to an OAuth account](https://supabase.com/docs/guides/auth/auth-identity-linking#how-to-add-emailpassword-sign-in-to-an-oauth-account). Auth POST verification issues an OTP session in [the tagged provider source](https://github.com/supabase/auth/blob/v2.197.0/internal/api/verify.go); this is why the new path keeps email proof and password update together instead of accepting a general OTP session on the old reset page.

That code was deployed from `staging` at [the development site](https://hotpizzaace-development.onrender.com), commit `c6c17a10decfa5310efdf1d49c06dd3ccb41fc6b`, [CI run 39481007720](https://github.com/Satya2n/hotpizzaace/actions/runs/39481007720), Render deployment `dep-dbbrpgou01pc73bphd10`. Live health returned HTTP 200 with database/commerce connected and payments simulated. A separate live request confirmed disabled reset requests returned `recovery_not_ready` without an email-sent notice. The hydrated live browser showed an enabled Google action, a disabled reset-send button and a configuration notice, with no stale expired-link message. No real password was entered or changed during those checks. Successful live email recovery was not established; the later owner password acceptance used the separate settings workflow in `7915b12`.

## Initial findings and fixes

- **Set up owner password** previously attempted signup. The nominated owner already has a verified Google identity, so this could return an intentionally generic confirmation notice without adding a password. Setup and forgot-password now both request an inbox recovery link for the existing account. Password entry happens only after the private link is verified.
- An authorized Google owner was automatically sent from the login page to the dashboard, including an explicit recovery request. Explicit `auth_action=reset` now remains on recovery; normal login behavior and membership checks stay intact.
- Recovery callback failures previously used Google cancellation feedback. Expired, reused or browser-mismatched links now return to recovery with a finite message and a fresh-link action. Provider descriptions, links, codes and tokens are never reflected in application feedback.
- The separate initial-account signup handler now checks returned local sign-out errors before claiming a confirmation notice. Hosted email autoconfirm must remain disabled; this is not a substitute for that configuration.

## Follow-up: correlate each browser verification request

The owner authorized inspection of the newest reset message. Its project, recovery type and application callback were correct. Gmail grouped messages and hid later bodies as trimmed content. One direct verification exceeded the provider's validity window and failed as expired. A subsequent link opened within a minute passed email verification but failed PKCE exchange with a code-challenge/verifier mismatch. No password was changed.

The installed Auth SDK stores separate verifier slots but, by default, does not append the slot's `sb_flow_id` to email redirects. Without that identifier the callback reads a legacy key for the most recently started flow. The shared client configuration now opts into `experimental.appendPkceFlowIdToRedirects` for server, browser and proxy clients. The existing callback forwards that identifier, and the existing exact-host wildcard callback allowlists accommodate the additional query parameter. Origin checks, verified recovery claims and membership checks remain intact.

Offline tests with the actual installed SDK and SSR cookie adapter reproduced a wrong verifier when requests overlapped without correlation, then verified that each identified callback selected its own verifier. An ordinary single recovery from an existing Google session succeeded in the fixture with either configuration, so the precise source of the live mismatch was not established. At that stage, newly generated live email still needed acceptance. That email approach was later deferred; the accepted owner password workflow does not depend on it. No mailbox contents, message IDs, link tokens or browser verification secrets are recorded here.

The correlated-link release `12dab77` was also tested live. Its newest email included the expected flow identifier and target. The source of the first request and precise live browser failure were not established.
